# Разработка «Печатает Максим»

## Начать с фактов

1. Открыть корень репозитория.
2. Полностью прочитать `AGENTS.md` и `docs/PROJECT_CONTEXT.md`.
3. Проверить текущую ветку, `git status`, `origin/main` и последние commit.
4. Если указан GitHub Issue или Pull Request, прочитать его до изменений.
5. Открывать `docs/DECISIONS.md`, `docs/UX_RULES.md` и другие документы только
   когда они относятся к задаче.
6. Сохранить чужие и несвязанные локальные изменения.

Если активен `docs/DEVELOPMENT_PROTOCOL.md`, после каждого завершённого или
блокированного действия сразу обновлять его статус, результат, проверку и
следующий шаг.

## Понимать короткие команды

- `Проанализируй` — выполнить read-only анализ и дать вывод с доказательствами.
- `Обсудим` или `Предложи` — предложить варианты; ничего не менять до
  согласования.
- `Реализуй`, `Исправь`, `Сделай` — внести локальные изменения и проверить их;
  не делать commit и push.
- `Проверь` — выполнить диагностику и релевантные тесты; не исправлять без
  отдельного указания.
- `Покажи` — запустить проект локально и проверить результат в браузере.
- `Commit` — проверить текущий scope и создать локальный commit; не отправлять
  его.
- `Отправь в GitHub` — проверить, создать commit при наличии согласованных
  изменений, отправить ветку и открыть Pull Request; не объединять.
- `Объединяй` — объединить готовый Pull Request после обязательных проверок.
- `Публикуй` — выполнить полный путь: проверить, создать commit при
  необходимости, отправить ветку, создать Pull Request, дождаться CI, объединить,
  дождаться deployment и проверить production.
- `Откати` — подготовить безопасный `git revert` через отдельную ветку и Pull
  Request; не использовать разрушительный reset.

Не расширять действие команды: анализ не разрешает правки, локальная реализация
не разрешает публикацию.

## Выполнить изменение

1. Кратко сообщить владельцу затрагиваемую область и критерий готовности.
2. Создать ветку `agent/<краткое-название>` от свежего `origin/main`, если
   работа ещё не изолирована.
3. Менять минимальный связный набор файлов.
4. Не смешивать изменение пользовательского сценария с инфраструктурным
   рефакторингом.
5. Для Studio сохранять mobile-first поведение на `390 × 844`, затем проверять
   `1440 × 900`.
6. Не переносить состояние из `app.js` в мобильный preview и не создавать
   второй store.
7. Если безопасное действие недоступно, записать точную блокировку и продолжить
   независимые шаги без запроса технических деталей у владельца.

## Выбрать минимальную проверку

- Любое изменение: `npm run check:fast`.
- Критический пользовательский путь: `npm run test:smoke`.
- Контент и шаг 01: `npm run test:studio-content`.
- Настройки и шаги 02–03: `npm run test:studio-settings`.
- Мобильный preview, загрузка и плавающая панель:
  `npm run test:studio-mobile`.
- Геометрия, границы, SVG и повторы: `npm run test:studio-production`.
- Перед Pull Request: `npm run check:pr`.
- Полный regression: `npm run check:full` для крупных или рискованных изменений;
  в обычном процессе его также запускает отдельный плановый workflow.

При падении теста сначала определить дефект продукта или нестабильность
сценария. Не маскировать причину увеличением timeout или безусловным retry.

## Обновлять контекст только по смыслу

Обновить `docs/PROJECT_CONTEXT.md`, если изменились точки входа, каталоги,
runtime-порядок, состояние, события, геометрия, форматы, команды, тестовые
наборы, CI или deployment.

Добавить новую запись в `docs/DECISIONS.md`, если принято устойчивое продуктовое
или архитектурное решение. Не переписывать старую запись задним числом.

Статус текущей задачи хранить в GitHub Issue или Pull Request. Не создавать
новые Markdown-файлы статуса или очереди.

## Работать с GitHub и production

1. Не отправлять изменения напрямую в `main`.
2. Сохранять обязательный статус `Lint and Playwright smoke tests`.
3. Перед push убедиться, что diff соответствует только текущей задаче.
4. Открывать Pull Request с результатом, причиной, проверками и рисками.
5. Объединять только после успешного обязательного CI.
6. После merge дождаться `Deploy to REG.RU`.
7. Проверить production `version.json`, главную страницу и `/studio/`.
8. При неудачном production использовать revert-ветку и новый Pull Request.

Секреты не читать, не печатать и не переносить в код или документацию.
