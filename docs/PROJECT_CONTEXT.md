# Контекст проекта «Печатает Максим»

Последняя проверка документа: 12 августа 2026 года.

Этот файл — короткая точка входа для нового разработчика или нового диалога с
ChatGPT/Codex. Его задача — дать рабочее понимание проекта без полного анализа
репозитория.

## Как начинать работу

Перед изменениями прочитать в таком порядке:

1. `AGENTS.md` — обязательные правила работы, проверок, commit и публикации.
2. Этот файл — карта кода и поток данных.
3. Связанные записи `docs/DECISIONS.md` — согласованные продуктовые и
   технические решения.
4. `docs/UX_RULES.md` — неизменяемые правила интерфейса, если задача влияет на
   пользовательский путь.
5. GitHub Issue или Pull Request текущей задачи — статус, критерии и передача.
6. `docs/ARCHITECTURE.md` — подробности текущей архитектуры и риски.
7. `docs/ROADMAP.md` и `TODO.md` — долгосрочные приоритеты, актуальность которых
   нужно сверять
   с владельцем проекта и последними commit.

Новый диалог с ChatGPT можно начинать так:

> Открой `AGENTS.md` и `docs/PROJECT_CONTEXT.md`, проверь актуальную ветку,
> рабочее дерево и связанный GitHub Issue. Реализуй задачу, выполни указанные
> проверки и обнови проектный контекст только при изменении устройства проекта.
> Ничего не публикуй без отдельной команды.

## Что представляет собой проект

Проект — статический сайт без backend и frontend-бандлера; перед публикацией
отдельный скрипт формирует allowlist-artifact:

- публичная страница объясняет продукт;
- `/studio/` позволяет загрузить логотип или ввести текст, настроить ленту и
  стикер, а затем сформировать заявку;
- шаг 03 отправляет заявку и production-SVG в приватный архив REG.RU, а
  Telegram используется как основной оперативный канал уведомления;
- production размещён на REG.RU;
- исходный репозиторий:
  `https://github.com/9627997/pechataet-maksim-site`;
- production:
  `https://печатаетмаксим.рф/`;
- production Studio:
  `https://печатаетмаксим.рф/studio/`.
- канонический домен: `https://печатаетмаксим.рф/`;
- в машинных URL используется эквивалентная Punycode-форма
  `https://xn--80aaarctnodv3agc9d.xn--p1ai/`;
- `print86.ru` и все `www`/HTTP-варианты должны делать один постоянный 301 на
  канонический HTTPS-домен с сохранением пути и параметров;
- состояние доменов и инструкции владельцу:
  `docs/DOMAIN_SEO_RUNBOOK.md`.

## Главные точки входа

| Область            | HTML                | CSS                                                                  | JavaScript       |
| ------------------ | ------------------- | -------------------------------------------------------------------- | ---------------- |
| Публичная страница | `index.html`        | `css/style.css`, `css/hero-v03.css`, `css/products-v04.css`          | `js/app.js`      |
| Актуальная Studio  | `studio/index.html` | `studio/assets/css/app.css`, `studio/assets/css/mobile-products.css` | см. порядок ниже |

Production-скрипты Studio подключаются как обычные `<script>` и зависят от
порядка:

1. `studio/assets/js/geometry.js`
2. `studio/assets/js/layout.js`
3. `studio/assets/js/smart-crop.js`
4. `studio/assets/js/trace-mask.js`
5. `studio/assets/js/trace-engine.js`
6. `studio/assets/js/app.js`
7. `studio/assets/js/mobile-products.js`

`geometry.js` публикует `window.RibbonStudioGeometry`, а `layout.js` использует
его и публикует `window.RibbonStudioLayout`. `smart-crop.js` локально анализирует
растровое изображение, предлагает рамку по лицам, фону или визуально значимой
области и публикует `window.RibbonStudioSmartCrop`. `trace-mask.js` отделяет
печатаемый знак от светлого или тёмного фона, оценивает риск полноформатной
плашки и публикует `window.RibbonStudioTraceMask`. `trace-engine.js` публикует
`window.RibbonStudioTrace` и выполняет построение контуров через отдельный
`trace-worker.js`; worker загружает локальную копию ImageTracerJS 1.2.6.
Главный `app.js` зависит от geometry, layout, trace-mask и trace-engine. Менять
порядок подключения нельзя без отдельной миграции.

## Пользовательский сценарий Studio

### 01 Создать

- при пустом проекте показывает только интерфейсный пример: официальный
  тестовый логотип, надпись «ленты по любви» шрифтом Comfortaa и отметку
  «Пример оформления»;
- автоматический шаг тестовой ленты рассчитывается по всей демонстрационной
  композиции, поэтому пример не пересекается и не показывает рекомендацию
  изменения шага;
- слишком широкий тестовый шаг пропорционально помещается в мобильный образец,
  не меняя реальный размер шага и поведение пользовательского макета;
- компактный предпросмотр расположен перед полями названия и загрузки, чтобы
  результат был виден сразу, но на мобильном экране оставлял в первом экране
  начало формы;
- пример не записывается в состояние, production SVG и заявку и полностью
  заменяется первым осмысленным пользовательским текстом или логотипом;
- выбор активного изделия: лента или стикер; основной образец показывает только
  выбранное изделие;
- вкладки выбора встроены в предпросмотр и отвечают только за объект
  редактирования, а переключатели с подписью «В комплекте» — только за наличие
  изделий в проекте;
- один узел предпросмотра и выбора изделия используется на всех ширинах: на
  desktop он находится в правой колонке, а при ширине до `900px` переносится в
  поток активного шага;
- при исключении активного изделия редактор автоматически переключается на
  оставшееся;
- первый введённый текст становится общим и появляется на обоих изделиях;
- отдельную надпись выбранного изделия можно создать, временно убрать или
  вернуть к общему значению;
- пробельный ввод считается пустым, а переносы, табуляция и повторные пробелы
  нормализуются; после 60 знаков показывается рекомендация без блокировки;
- первый загруженный логотип становится общим и появляется на обоих изделиях;
- отдельный логотип выбранного изделия можно заменить, временно убрать или
  вернуть к общему значению;
- поддержка SVG, PNG, JPEG и первой страницы PDF;
- crop для непрозрачного растра;
- автоматическое предложение области crop с ручной корректировкой и явным
  fallback при низкой уверенности;
- положительная печатная маска по умолчанию удаляет светлую либо тёмную фоновую
  плашку и оставляет буквы и элементы логотипа; пользователь может явно выбрать
  обратный вариант «Печатать фон»;
- перед ImageTracer каждый вариант печатной маски плотно обрезается по
  фактическим печатаемым пикселям с небольшим защитным полем; пропорция
  автоматически созданного SVG рассчитывается по этим очищенным границам, а не
  по всему холсту crop;
- одноцветная автоматическая трассировка настоящими SVG-контурами в Web Worker;
- пользователь может оставить только текст или только логотип и добавить
  отсутствующий объект позже;
- шаги 02–03 недоступны, пока нет осмысленного текста или успешно обработанного
  логотипа;
- на мобильном пустые зоны «Ваш логотип» и «Ваш текст» ведут к соответствующим
  общим полям шага 01 и не являются частью макета.

### 02 Настроить

- выбор активного изделия: лента или стикер;
- показываются только настройки выбранного изделия;
- единый предпросмотр также показывает только выбранное изделие;
- сводка сообщает, использует изделие общий или собственный текст и логотип;
- быстрые действия возвращают в шаг 01 к надписи или логотипу выбранного
  изделия;
- изменение шрифта, цвета печати, размеров и положения;
- горизонтальное перемещение композиции ленты меняет шаг между повторами;
- вертикальное перемещение меняет положение внутри ленты;
- текст и логотип не загружаются заново как часть обычных настроек;
- автоматическая и ручная компоновка хранятся отдельно для каждого изделия.
- настройки текста показываются только при наличии текста, настройки логотипа —
  только при наличии логотипа; отсутствующий элемент предлагается добавить
  явным действием в сводке содержимого.

### 03 Получить

- состав управляется тумблерами в живом предпросмотре, а селекторы количества
  позволяют выбрать объём или вариант «Не заказывать» и синхронизируются с
  тумблерами;
- отдельная повторная карточка состава и производственный шаг на этом экране не
  показываются; хотя бы одно изделие всегда остаётся в заказе;
- компактная проверка состава заказа с живым мобильным предпросмотром без
  декоративных режимов «Комплект», «Макро» и «Упаковка»;
- итоговый предпросмотр не показывает hover-подсказки, рамки или выделение
  активного изделия из режима настройки;
- отправка заявки и production-SVG в same-origin endpoint `POST /api/orders/`;
- явный выбор предпочтительного ответа — телефон или Telegram; форма показывает
  и требует контакт только выбранного типа, а выбор сохраняется в заявке и
  уведомлениях;
- подтверждение показывается только после записи приватного архива и содержит
  серверный номер заявки;
- локальная текстовая копия остаётся доступной как fallback.

## Единый предпросмотр изделий

Реализация находится в:

- `studio/assets/js/mobile-products.js`;
- `studio/assets/css/mobile-products.css`;
- HTML-контейнер — `.mobile-products-panel` в `studio/index.html`.

Один DOM-компонент используется на всех ширинах и синхронизируется с теми же
layout-данными, что и production SVG. На desktop он расположен в правой колонке
и масштабируется CSS; при ширине до `900px` переносится перед полями активного
шага. Только мобильное плавающее поведение включается при `max-width: 700px`.

Предпросмотр:

- на шаге 01 показывает один выбранный образец в полезном крупном размере;
- на шаге 01 в плавающем компактном режиме занимает всю полезную ширину одним
  активным изделием, а состав комплекта открывается только при разворачивании;
- использует презентационные состояния `flow`, `dock-compact`, `dock-expanded`
  и `dock-keyboard`, которые не дублируют состояние проекта;
- при открытой экранной клавиатуре на шаге 01 превращается в узкую live-панель
  без переключателей состава и восстанавливает прежний вид после её закрытия;
- в плавающем режиме шага 01 показывает один полный повтор ленты с равномерным
  масштабированием по обеим осям либо центрированный стикер полезного размера;
- выбор ленты или стикера синхронизирован с редактором содержимого;
- явные вкладки редактирования находятся внутри карточки предпросмотра, а
  переключатели состава отделены подписью «В комплекте»;
- переключатели на всех трёх шагах управляют составом проекта, при этом хотя бы
  одно изделие всегда остаётся включено;
- на шаге 01 является основной визуализацией на любой ширине;
- на шаге 02 позволяет выбрать изделие нажатием в любой части образца;
- поддерживает перемещение логотипа и текста;
- становится плавающим при прокрутке;
- может разворачиваться и сворачиваться;
- использует те же layout-данные, что и основные SVG-превью.

Старый настольный showcase не показывается пользователю. Его `scene-kit` и SVG
остаются скрытым production-слоем: они нужны для расчётов и формирования
печатных файлов, но не создают вторую модель предпросмотра.

Центральный элемент ленты и соседние повторы должны использовать один шаг и одну
геометрию. Невидимая touch-область может быть больше рисунка, но видимая маска
выделения должна совпадать с фактическими закрашенными границами текста или
логотипа с зазором около 2 px. Для текста используются границы глифов, а не
line-height; у SVG пустые поля исходного `viewBox` удаляются при загрузке.
Физическая печатная зона остаётся отдельным направляющим слоем и не подменяет
рамку выбранного объекта.

Подсказки пустых зон существуют только в DOM мобильного интерфейса. Их нельзя
записывать в `state`, `data-studio-content`, production SVG или файл заявки.

## Главный поток данных Studio

```text
Поля и кнопки
      ↓
state в app.js
      ↓
нормализация общего и индивидуального контента
      ↓
geometry.js → физические печатные границы
      ↓
layout.js → координаты логотипа и текста
      ↓
render() в app.js
      ├── production SVG
      ├── production SVG в скрытом слое
      └── DOM-события → единый preview в mobile-products.js
```

`studio/assets/js/app.js` пока является главным координатором и содержит:

- состояние проекта;
- нормализацию и миграцию сохранённого состояния;
- загрузку и обработку файлов;
- координацию crop, выбор варианта печати и вызов отдельного движка трассировки;
  анализ предлагаемой области выполняет `smart-crop.js`, а чистую бинарную
  маску, её плотные печатные границы и оценку фоновой плашки строит
  `trace-mask.js`;
- синхронизацию контролов;
- вызов layout;
- отрисовку ленты и стикера;
- обновление production SVG и публикацию данных для единого предпросмотра;
- каталог runtime-значений и расчёт цены;
- сохранение проекта;
- формирование заявки.

Архитектурный аудит от 2 августа 2026 года подтвердил, что этот файл — главный
hotspot проекта: в нём около 4,5 тысячи строк, а изменение одной функции часто
затрагивает состояние, DOM, несколько предпросмотров, `localStorage` и
браузерные сценарии одновременно. Это основная причина высокой стоимости
небольших изменений, а не размер репозитория в целом.

`render()` сейчас одновременно пересчитывает макет, обновляет все сцены,
сохраняет состояние и публикует данные для мобильного интерфейса. Это известный
технический долг. Декомпозировать его нужно по одному модулю, без одновременного
изменения UX и без большого одномоментного переписывания интерфейса.

## Состояние и наследование контента

Состояние объявлено в начале `studio/assets/js/app.js`.

Ключевые части:

- `panel`: `upload`, `settings` или `order`;
- `content.logo.common` и `content.text.common`: общий контент шага 01;
- `content.logo.ribbon/sticker` и `content.text.ribbon/sticker`: наследование
  или индивидуальная версия изделия;
- `productStyles.ribbon/sticker`: шрифт, цвет, масштаб, offsets и `layoutMode`;
- `activeSettingsProduct`: изделие, настройки которого открыты;
- `activeContentProduct`: изделие, содержимое которого открыто на шаге 01;
- `repeatMm` и `repeatMode`: шаг повторов ленты;
- `meters` и `stickerQty`: одновременно определяют состав заказа;
- `currentLayouts`: актуальная геометрия ленты и стикера.

Правило разрешения контента:

```text
индивидуальное значение изделия
        ↓ если отсутствует или mode = inherit
общее значение шага 01
        ↓ если пользователь ещё ничего не ввёл
демонстрационный контент
```

Старые поля `state.font`, `state.print`, `state.fontSize`, `state.logoScale` и
часть offsets остаются совместимыми alias. Новую логику следует строить на
`productStyles`, не расширяя legacy-слой.

Одно и то же состояние сейчас представлено в нескольких формах:

- канонические `content` и `productStyles` в `app.js`;
- совместимые legacy-alias внутри `state`;
- значения полей формы;
- сериализованные snapshots в `document.body.dataset`;
- `CustomEvent`, которыми основной и мобильный runtime обмениваются
  изменениями.

Это переходная совместимость, а не целевая модель. При упрощении legacy-формат
следует нормализовать один раз на границе восстановления, после чего runtime
должен работать с одним каноническим состоянием. Миграции старых сохранённых
проектов нельзя удалять без явного решения и regression-теста.

## Хранение

- ключ `localStorage`: `ribbon-studio-v042`;
- восстановление выполняется при загрузке Studio;
- сбой или старый формат сохранения не должен блокировать чистый запуск;
- большие производные `data:`-изображения по возможности не дублируются;
- сброс проекта удаляет этот ключ.

Изменение shape сохраняемого состояния требует миграции/нормализации и теста
восстановления старого проекта.

## Геометрия

`studio/assets/js/geometry.js`:

- вычисляет печатные области ленты и стикера;
- знает физические размеры и поля печати;
- сериализует production SVG.

`studio/assets/js/layout.js`:

- размещает логотип и текст;
- сохраняет пропорции логотипа;
- предотвращает пересечение;
- ограничивает объекты печатной областью;
- возвращает layout и признак валидности.

Критические инварианты:

- логотип и текст не выходят за ленту или стикер;
- логотип не искажается;
- одинаковый layout используется всеми предпросмотрами;
- ручное перемещение не отменяет физические ограничения;
- изменение цвета печати одинаково применяется к тексту и логотипу;
- повторы ленты имеют равный шаг и не обрезают текст.

## Связь `app.js` и `mobile-products.js`

Скрипты взаимодействуют через DOM и `CustomEvent`.

Основные события:

| Событие                            | Отправитель          | Назначение                           |
| ---------------------------------- | -------------------- | ------------------------------------ |
| `studio:content-state-updated`     | `app.js`             | общий/индивидуальный текст и логотип |
| `studio:layout-updated`            | `app.js`             | готовые layout ленты и стикера       |
| `studio:product-selection-updated` | `app.js`             | фактический состав заказа            |
| `studio:product-selection-change`  | `mobile-products.js` | пользователь переключил ленту/стикер |
| `studio:content-product-change`    | `mobile-products.js` | выбран объект содержимого шага 01    |
| `studio:content-edit-request`      | `mobile-products.js` | запрошен текст или логотип изделия   |
| `studio:settings-product-change`   | `mobile-products.js` | выбран объект для шага 02            |
| `studio:transform-delta`           | `mobile-products.js` | drag изменил позицию или шаг         |
| `studio:logo-upload-target-set`    | тестовый интерфейс   | задан target загрузки логотипа       |

При добавлении нового события документировать `detail`, направление и владельца
состояния. `mobile-products.js` не должен становиться вторым независимым store.

Сейчас `mobile-products.js` частично восстанавливает модель из
`document.body.dataset`, полей формы, DOM-изображений и событий, а затем отдельно
размещает текст, логотип и повторы ленты. Поэтому изменение state shape или
рендеринга может требовать согласованных правок в обоих JS-файлах. Целевая
граница — один готовый snapshot состояния и layout от основного runtime;
мобильный модуль должен только отображать его и отправлять пользовательские
действия, не вычисляя параллельную модель проекта.

## Production SVG

Для получения производственной разметки используется:

```js
window.RibbonStudioProduction.serialize('ribbon');
window.RibbonStudioProduction.serialize('sticker');
```

API публикуется `app.js`. Пустая строка означает отсутствие нужного SVG.
Production SVG должен сохранять печатные границы независимо от визуальных
масштабов страницы.

## Шрифты

- файлы находятся в `studio/assets/fonts/`;
- список вариантов пока задан в `FONT_OPTIONS` внутри `app.js`;

  только техническое название;

## Данные продукта

`studio/data/product.json` содержит справочное описание поддерживаемых размеров,
форматов и возможностей. Часть runtime-значений пока продублирована в HTML и
JavaScript, поэтому изменение только этого JSON не обязательно меняет
интерфейс. Перед правкой продукта искать все использования значения.

Размеры, количества, цены, форматы и значения по умолчанию сейчас находятся в
нескольких местах: `product.json`, `studio/index.html` и `app.js`.
`product.json` не является runtime-источником истины, хотя входит в deployment
artifact. Безопасное направление упрощения — единый валидируемый каталог,
который используют состояние, интерфейс, pricing и тесты.

## Подтверждённый архитектурный долг

Аудит от 2 августа 2026 года зафиксировал:

- `studio/assets/js/app.js` совмещает слишком много ответственностей;
- трассировка контуров вынесена в `trace-engine.js`/`trace-worker.js`, а чистая
  подготовка печатной маски — в `trace-mask.js`; координация crop и вариантов
  результата пока остаётся в `app.js`;
- legacy-alias синхронизируются с каноническим состоянием во время обычного
  runtime, а не только при восстановлении старого проекта;
- основной и мобильный runtime частично дублируют подготовку данных и
  рендеринг;
- каталог изделий и pricing не имеют единственного источника истины;
- `studio/index.html`, `studio/assets/css/app.css` и
  `studio/assets/css/mobile-products.css` остаются крупными связанными файлами;
- Playwright хорошо защищает пользовательские сценарии, но быстрых unit-тестов
  для состояния, миграций, каталога, pricing и чистой геометрии пока нет;
- проверенные исторические исходники и неподключённые заготовки удалены;
  `css/products-v04.css` остаётся активным стилем публичной страницы.

Публичные legacy-URL должны продолжать создаваться
`scripts/build-deploy.mjs` как переходы на `/studio/`.

Безопасная последовательность упрощения без изменения UX:

1. создать единый каталог изделий и вынести чистый расчёт цены;
2. добавить unit-тесты состояния, миграций, pricing, geometry и layout;
3. нормализовать legacy-состояние только при восстановлении;
4. передавать мобильному preview один snapshot состояния и layout;
5. извлекать из `app.js` по одному модулю: каталог, состояние, обработку файлов,
   crop/трассировку, заявку и только затем UI-координатор.

Каждый шаг должен быть отдельной задачей без одновременной смены
пользовательского сценария. Нельзя создавать второй store, удалять поддержку
старых сохранений без миграции или выполнять большой переход на новый
UI-фреймворк одним изменением.

## Проверки

```bash
npm run check:fast
npm run benchmark:trace
npm run test:smart-crop
npm run test:trace-mask
npm run test:order-receiver
npm run check:pr
npm run check:full
npm run test:smoke
npm run test:studio-content
npm run test:studio-settings
npm run test:studio-mobile
npm run test:studio-production
npm run test:mobile
npm run test:desktop
npm test
```

- `check:fast` форматирует и проверяет только изменённые файлы, не запускает
  браузер;
- `benchmark:trace` запускает изолированное сравнение текущей построчной
  трассировки, VTracer и ImageTracerJS; отчёт, SVG и сравнительный лист
  записываются в игнорируемый каталог `test-results/trace-benchmark/` и не
  подключаются к Studio или deployment artifact;
- `test:smart-crop` проверяет локальный анализ центрального и смещённого
  объекта, fallback на ручную рамку и ветку обнаружения лица;
- `test:trace-mask` проверяет положительную полярность для тёмного и светлого
  знака, прозрачный PNG, полупрозрачную плашку и настоящий рамочный логотип;
- `test:order-receiver` проверяет синтаксис PHP-приёмника и обязательные поля
  публичного ответа;
- `check:pr` выполняет общую проверку, сборку artifact и критические сценарии
  `@smoke`;
- `check:full` выполняет весь regression и используется отдельным workflow;
- тематические команды позволяют проверять только затронутую часть Studio.

Playwright-конфигурация:

- mobile: `390 × 844`;
- desktop: `1440 × 900`;
- Chromium;
- общие helpers: `tests/helpers/studio.js`;
- сценарии: `tests/site.smoke.spec.js`, `tests/studio-content.spec.js`,
  `tests/studio-settings.spec.js`, `tests/studio-mobile.spec.js` и
  `tests/studio-production.spec.js`.

Полный regression остаётся достаточно быстрым для итоговой проверки, но почти
все продуктовые правила сейчас проверяются через браузер. При выделении чистого
ядра нужны unit-тесты, которые локализуют ошибки состояния, миграций, pricing и
геометрии до запуска Playwright. Существующие end-to-end сценарии при этом
остаются обязательной защитой пользовательского пути.

После изменения Studio обязательно проверить:

- SVG, прозрачный/непрозрачный PNG, JPEG и первую страницу PDF;
- crop и автоматическую трассировку;
- цвет ленты и цвет печати;
- масштаб и центровку текста;
- масштаб и центровку логотипа;
- границы ленты и стикера;
- шаг повторов;
- ширины 390 и 1440 px;
- отсутствие горизонтального скролла.

Во время разработки допустим тематический тест. Перед публикацией нужен полный
набор, если только явно не зафиксирована причина, почему он недоступен.

## GitHub и публикация

- основная ветка: `main`;
- рабочие ветки: `agent/<краткое-название>`;
- одна законченная задача — один commit;
- commit и push выполняются только по отдельной явной команде владельца;
- проверки PR: `.github/workflows/studio-tests.yml`;
- автоматическая проверка документации:
  `scripts/check-project-docs.mjs` / `npm run docs:check`;
- шаблон PR: `.github/pull_request_template.md`;
- шаблон GitHub Issue: `.github/ISSUE_TEMPLATE/change.yml`;
- текущая работа и её статус: GitHub Issues/Projects;
- журнал устойчивых решений: `docs/DECISIONS.md`;
- deployment: `.github/workflows/deploy-reg-ru.yml`;
- полный regression: `.github/workflows/full-regression.yml`;
- публичный deployment artifact создаёт
  `scripts/build-deploy.mjs` / `npm run build:deploy`;
- generated-каталог `_site/` содержит только публичные страницы и runtime-ресурсы
  и не хранится в Git;
- корневой `.htaccess` входит в artifact и выполняет единый прямой 301 с HTTP и
  `www` на канонический HTTPS-домен; встроенные редиректы сайта в ISPmanager
  должны оставаться выключенными, чтобы не создавать цепочки;
- каждый artifact содержит `version.json` с точным commit и временем сборки;
- cache-version главного `studio/assets/js/app.js` в `studio/index.html` равен
  первым 12 символам SHA-256 файла; smoke-тест требует обновить URL после
  каждого изменения скрипта, поскольку REG.RU длительно кеширует JS;
- merge/push в `main` публикует статические файлы на REG.RU;
- обязательный Pull Request один раз выполняет `check:pr`;
- deployment не повторяет lint и Playwright: он собирает artifact, публикует и
  проверяет production;
- полный regression запускается вручную и по расписанию в рабочие дни;
- workflow сохраняет artifact на 14 дней, синхронизирует его с production и
  проверяет commit в `version.json`, главную, Studio, `robots.txt`, sitemap и
  ровно один переход для каждого HTTP-, `www`- и альтернативного домена;
- production deployment выполняются последовательно; новая публикация не
  прерывает уже начатую синхронизацию;
- Studio отправляет шаг 03 в `POST /api/orders/`; приёмник сохраняет заявку и
  production-SVG в приватном каталоге вне web-root, после чего возвращает номер;
- повтор одного `requestId` идемпотентен, уведомления Telegram, MAX и Google не
  определяют факт приёма, а локальная текстовая копия остаётся fallback;
- приватная конфигурация каналов хранится только на REG.RU по пути вне web-root;
  runtime-настройка описана в `docs/ORDER_RECEIVER_RUNBOOK.md`;
- deployment требует environment-secrets `PM_TELEGRAM_BOT_TOKEN` и
  `PM_TELEGRAM_CHAT_ID`, проверяет бота и чат через Telegram API, а затем по SSH
  устанавливает приватную конфигурацию приёмника с правами `600`;
- служебные каталоги `docs`, `tests`, `scripts`, `.github` и исходные файлы
  разработки не должны попадать в web-root;
- прежние публичные URL `constructor.html` и
  `ribbon-studio-design-system-v1.html` сохраняются в artifact только как
  переходы на актуальную `/studio/`, без исторического runtime;
- workflow deployment также поддерживает ручной `workflow_dispatch` и связан с
  GitHub Environment `production`.
- production-проверка требует HTTP 405 от `GET /api/orders/`, подтверждая, что
  REG.RU исполняет PHP endpoint, а не отдаёт его исходный файл;

Секреты REG.RU находятся в GitHub Actions. Их нельзя копировать в код,
документацию, сообщения или локальные `.env`.

## Источники правды

При конфликте использовать следующий приоритет:

1. явная текущая задача владельца;
2. `AGENTS.md`;
3. работающие тесты и production-runtime;
4. `docs/UX_RULES.md`;
5. `docs/DECISIONS.md`;
6. этот файл и `docs/ARCHITECTURE.md`;
7. `docs/ROADMAP.md`, `TODO.md`, changelog и исторические заметки.

Если документация расходится с кодом, сначала подтвердить фактическое поведение,
затем исправить документацию в той же задаче.

## Правила безопасного параллельного развития

- каждый участник начинает новую задачу от свежего `origin/main`;
- один участник — одна ветка;
- каждый участник берёт отдельный GitHub Issue или явно ограниченную локальную
  задачу;
- не редактировать одновременно один участок `app.js` без согласования;
- не менять state shape, события или геометрию молча;
- не смешивать рефакторинг и изменение UX в одном commit;
- перед передачей работы оставить понятный статус;
- не использовать `git reset --hard` и не удалять чужие изменения.

## Когда обновлять этот файл

Обновление обязательно в той же задаче, если изменились:

- production-точки входа или порядок скриптов;
- shape состояния или ключ `localStorage`;
- публичные DOM-события;
- геометрия и её владелец;
- поддерживаемые форматы, изделия или размеры;
- команды запуска и тестов;
- GitHub-процесс или hosting;
- назначение крупных каталогов;
- критические UX-инварианты.

Мелкие стили, исправления текста и внутренний рефакторинг без изменения карты
проекта обновления этого файла не требуют.

Текущую работу, ближайшие шаги, блокировки и передачу фиксировать в GitHub
Issue или Pull Request, не перегружая ими устойчивую карту архитектуры.
