# План безопасной миграции альтернативного лендинга

**Проект:** «Печатает Максим»  
**Исходный репозиторий:** `https://github.com/9627997/pechataet-maksim-site`  
**Канонический production-домен:** `https://печатаетмаксим.рф/`  
**Дата:** 13 августа 2026 года

## Цель

Перевести альтернативный лендинг из изолированного прототипа в репозиторий и, при подтверждении качества, сделать его новой главной страницей без потери текущего функционала Studio, обработки логотипов, crop, перевода растров в SVG, определения безопасных полей, сохранения проектов, заявок, уведомлений и SEO/GEO-сигналов для Яндекса и Google.

Ключевой принцип миграции — **сначала интеграция без переключения production**, затем проверка, затем обратимое включение. Текущий `main` нельзя заменять до прохождения функциональных, SEO и smoke-проверок.

> Альтернативный лендинг должен менять в первую очередь информационную архитектуру и входной сценарий. Алгоритмы crop, mask, tracing, geometry, layout, order receiver и уведомления не следует переписывать в рамках этой миграции.

## Что уже есть в текущей архитектуре

| Область | Текущая реализация | Правило сохранения |
|---|---|---|
| Главная | `index.html`, `css/`, `js/app.js` | До переключения production остаётся неизменной |
| Studio | `studio/index.html` и runtime в `studio/assets/js/` | Не переносить и не переписывать ради нового лендинга |
| Crop | `smart-crop.js` и crop-modal в Studio | Оставить текущий алгоритм и ручную корректировку |
| Фото → логотип | `trace-mask.js`, `trace-engine.js`, `trace-worker.js` | Использовать текущую pipeline без изменения формата данных |
| Безопасные поля | `geometry.js`, layout-ограничения и print guides | Проверить regression, но не дублировать в новом UI |
| Состояние | `localStorage` с ключом `ribbon-studio-v042` | Не менять ключ, схему восстановления или legacy aliases |
| Заявки | `POST /api/orders/`, PHP receiver, архив, Telegram/Google Apps Script | Не менять контракт запроса и серверную обработку |
| Deployment | `scripts/build-deploy.mjs`, GitHub Actions, REG.RU | Добавить прототип только после проверки allowlist и artifact |
| SEO | canonical, robots, sitemap, Open Graph, Schema.org | Сохранить канонический Punycode URL и структуру сущностей |

## Этап 0. Зафиксировать baseline production

До изменения `index.html` нужно сохранить текущий commit, production HTML и контрольные показатели. В отдельном документе или issue зафиксировать текущие значения title, description, canonical, robots, Open Graph, JSON-LD, ссылки на Studio, телефон, sitemap и robots.txt.

Также следует сохранить список активных production-путей: `/`, `/studio/`, `/api/orders/`, старые redirect-URL, `robots.txt`, `sitemap.xml`, `version.json` и любые URL, которые создаёт deployment-сборка. Для заявок необходимо зафиксировать реальный smoke-сценарий с тестовым запросом в безопасной среде, не отправляя ложную заявку в production без согласования.

**Контрольная точка:** есть baseline commit, копия текущего `index.html`, список URL и подтверждение, что `main` чистая.

## Этап 1. Создать отдельную ветку и сохранить изоляцию

Работу вести в отдельной ветке, например `ux-alternative-homepage`. Альтернативный лендинг уже можно хранить в `prototypes/homepage-alternative/`; до принятия решения он не должен подменять `index.html` и не должен попадать в production artifact автоматически.

На этом этапе допустимы только статические файлы альтернативной страницы и её README. Не следует копировать Studio runtime в прототип и не следует подключать `studio/assets/js/app.js` на главной: это повысит риск конфликтов, двойной инициализации состояния и случайной отправки заявки.

**Контрольная точка:** текущая главная и Studio открываются по прежним URL, а альтернативная страница доступна только по отдельному локальному или preview-пути.

## Этап 2. Ввести единый контракт перехода в Studio

Альтернативный лендинг должен передавать контекст выбора через параметры:

```text
/studio/?product=ribbon
/studio/?product=sticker
/studio/?product=set
/studio/?product=ribbon&material=satin
/studio/?product=ribbon&material=silicone
```

Рекомендуемые допустимые значения нужно нормализовать в одном небольшом адаптере. Не следует передавать в URL текст пользователя, SVG, base64, данные crop или персональные данные. URL передаёт только стартовый продукт и, если возможно, материал.

В Studio адаптер должен выполняться до первого `render()` и только устанавливать начальные значения `bundle`, `activeContentProduct`, `activeSettingsProduct` и материал в UI. Он не должен менять существующий `content` model, `productStyles`, `cropState`, `traceInfo`, `localStorage` schema или order payload.

После чтения параметров Studio должна показать контекстный баннер: «Вы создаёте макет ленты», «Вы создаёте макет стикера» или «Вы создаёте комплект». При входе из `product=ribbon` лента становится активной, стикер остаётся дополнительным продуктом; при `product=sticker` активным становится стикер; при `product=set` сохраняется текущая комплектная модель.

Если материал ещё не поддерживается как полноценное поле в Studio, параметр `material` нельзя выдавать за завершённый выбор. В этом случае нужно показать: «Материал уточним после заявки; сейчас настройте внешний вид».

**Контрольная точка:** прямой вход на `/studio/` без параметров сохраняет старое поведение, а вход с параметрами только выбирает стартовый сценарий и не меняет последующую работу редактора.

## Этап 3. Подключить альтернативную страницу за feature flag или preview-маршрутом

Безопаснее всего сначала опубликовать альтернативу по отдельному preview URL, например `/prototypes/homepage-alternative/` на staging или временном preview-хосте. Если нужен тест на реальном домене, использовать краткоживущий query-параметр или cookie для внутренней аудитории, но не индексировать preview-вариант.

На этом этапе production `/` остаётся текущей страницей. Не нужно создавать индексируемую копию на `/alternative-homepage/`: это может породить дублирование контента и канонические конфликты. Для любого временного preview URL использовать `noindex, nofollow` или ограничение на уровне preview-окружения, а в sitemap его не добавлять.

Feature flag должен быть серверным или deployment-level, а не только визуальным JavaScript-переключателем после загрузки страницы. Если возможно, использовать две версии artifact и быстрый выбор целевого файла в deployment-процессе. Это обеспечивает чистый HTML для поисковых роботов и упрощает rollback.

## Этап 4. Интеграционное тестирование без потери функционала

### 4.1. Проверки лендинга

Нужно проверить desktop 1440 px и mobile 390 px, отсутствие горизонтального скролла, доступность клавиатурной навигации, focus states, читаемость CTA и корректность работы мобильного sticky CTA. Все три карточки продукта должны вести на ожидаемый параметризованный URL.

Проверить hero, product cards, material links, FAQ, финальную CTA, телефонные ссылки, якорную навигацию и загрузку существующих изображений и SVG. Ошибка загрузки дополнительного декоративного изображения не должна блокировать CTA.

### 4.2. Проверки Studio

Проверить вход без параметров и входы с каждым `product`/`material` значением. Затем выполнить существующую матрицу: текст, SVG, PNG, JPEG и первая страница PDF; crop с автоматическим предложением и ручной корректировкой; перевод растрового логотипа в SVG; выбор фоновой или знаковой маски; цвет ленты; цвет печати; размер и центровка текста; масштаб и центровка логотипа; удержание элементов внутри safe area.

Отдельно проверить, что после перехода из нового лендинга не меняется `localStorage`, не ломается восстановление проекта, не исчезает demo preview, не меняются названия production SVG и не меняется order payload.

### 4.3. Проверки интеграций

Проверить `POST /api/orders/`, idempotency key, повторную отправку, серверный номер заявки, приватный архив, локальную fallback-копию, Telegram-уведомление и Google Apps Script-дублирование. На production нельзя отправлять тестовые персональные данные без согласования; использовать тестовый receiver или заранее оговорённый безопасный режим.

### 4.4. Регрессионные команды

Минимальный набор перед Pull Request:

```bash
npm run check:fast
npm run check:pr
npm run test:smart-crop
npm run test:trace-mask
npm run test:order-receiver
npm run test:studio-mobile
npm run test:studio-production
```

В текущем проекте полный `check:pr` уже подтверждал прохождение 32 тестов при 2 пропущенных сценариях в доступном окружении. После добавления адаптера входного контекста этот результат нужно повторить на чистой ветке.

## Этап 5. Сохранить Яндекс и Google SEO/GEO

### 5.1. Канонический домен и зеркала

Каноническим остаётся `https://xn--80aaarctnodv3agc9d.xn--p1ai/`, который браузер показывает как `https://печатаетмаксим.рф/`. Не менять canonical на `print86.ru`, `www` или preview-путь. Все существующие правила 301 должны сохранять путь и query и не создавать цепочек переходов.[1]

Параметры `?product=...` в Studio не должны становиться индексируемыми посадочными страницами. Для Studio можно использовать canonical на `/studio/`, а при необходимости — `noindex,follow` для параметризованных URL. Главная страница должна иметь один canonical без query.

### 5.2. Title, description и контент

Новый hero-текст можно сделать более конверсионным, но нельзя потерять подтверждённые сущности: «Печатает Максим», печать лент с логотипом, наклейки и стикеры, сатин и силикон, Нижневартовск, ХМАО, подготовка макета онлайн. Title и description должны оставаться уникальными, точными и соответствовать фактическим услугам.[1]

Не добавлять неподтверждённые товары или географию ради охвата. Для GEO важнее согласованность названия, региона, телефона, услуг, канонического URL и карточек организации, чем искусственное повторение ключевых слов.

### 5.3. Schema.org, Open Graph и изображения

Перенести или сохранить текущий JSON-LD `Organization`, `WebSite`, `WebPage` и два `Service`. Если добавляются новые карточки продукта, не создавать ложные `Product` с ценой, если цена не является постоянной и подтверждённой. Сохранить `og:title`, `og:description`, `og:url`, `og:image`, Twitter card и alt-тексты. У hero-изображения оставить размеры, `fetchpriority="high"` и описательный alt.

### 5.4. Robots и sitemap

Не добавлять preview-каталог и альтернативные URL в `sitemap.xml`. Проверить, что production `/` и `/studio/` остаются доступными для обхода, а query-варианты Studio не создают индексируемые дубли. После переключения повторно проверить robots.txt, sitemap и `version.json` в deployment artifact.

### 5.5. Переобход и мониторинг

После production-переключения в Яндекс Вебмастере отправить на переобход главную и Studio, проверить главное зеркало и региональность Нижневартовска. В Google Search Console проверить главную и Studio через URL Inspection, sitemap и видимый canonical. Не менять одновременно домен, структуру URL и весь контент: иначе невозможно будет отделить эффект редизайна от миграционного сигнала.

## Этап 6. Аналитика и A/B-подход

До переключения сохранить baseline конверсий: клик по hero CTA, клик по ленте, стикеру и комплекту, начало ввода текста, загрузка файла, просмотр расчёта и отправка заявки. В новой версии добавить события `homepage_cta_click`, `product_entry_ribbon`, `product_entry_sticker`, `product_entry_set`, `material_entry_satin`, `material_entry_silicone`, `studio_context_seen`, `studio_first_input`, `studio_quote_view` и `application_submit`.

Если подключается Яндекс Метрика, использовать фактический счётчик владельца и не придумывать идентификатор. Google Analytics не обязателен для первого запуска, если нет подтверждённой потребности в Google Ads или единой аналитической воронке.[1]

Первый запуск лучше провести как последовательное сравнение старой и новой версии, а не как одновременный SEO-A/B-тест на индексируемом URL. Если нужен эксперимент, делить трафик только после проверки, что поисковым роботам отдаётся стабильная canonical-версия и нет cloaking.

## Этап 7. Staged rollout

| Фаза | Production-состояние | Что проверяем | Условие перехода |
|---|---|---|---|
| 0. Baseline | Текущая главная | SEO, заявки, Studio, метрики | Снимки и контрольные значения сохранены |
| 1. Preview | Альтернатива на неиндексируемом пути | Визуальный UX и все CTA | Нет критических ошибок |
| 2. Internal | Альтернатива для владельца и команды | Реальные сценарии без ложных заявок | Подтверждены продуктовые входы |
| 3. Canary | Новая главная для небольшой доли прямого трафика | Ошибки, заявки, скорость, конверсия | Метрики не хуже baseline и нет SEO-ошибок |
| 4. Full switch | Новая главная на `/` | Полная воронка и поисковая доступность | Владелец подтверждает переход |
| 5. Observation | Новая главная | 7–14 дней мониторинга | Нет регрессий и аномалий |

## Rollback-процедура

Rollback должен быть заранее проверен в staging. Минимальный вариант — вернуть предыдущий `index.html` и CSS/JS в deployment artifact, не откатывая Studio runtime и `/api/orders/`. Если новый лендинг использует отдельный deployment flag, rollback выполняется переключением flag на старую главную.

После rollback проверить HTTP 200 для `/`, canonical, title, robots, sitemap, доступность `/studio/`, открытие заявки и отсутствие изменений в `POST /api/orders/`. В Search Console и Вебмастере не следует удалять страницы или менять canonical во время короткого технического rollback, если URL остаются теми же.

## Definition of Done

| Область | Критерий готовности |
|---|---|
| Изоляция | Старые `index.html`, Studio runtime и order receiver не ломаются при preview |
| UX | Лента, стикер и комплект имеют понятные входы и корректные CTA |
| Studio | Query-контекст выбирает стартовый продукт без изменения логики crop/tracing/layout |
| Изображения | Crop, mask, SVG tracing и safe fields проходят существующие проверки |
| Интеграции | Заявка, архив, Telegram, Google Apps Script и fallback проходят smoke-проверки |
| SEO | Один canonical, валидные meta/JSON-LD, robots/sitemap без preview-дублей |
| GEO | Сохраняются бренд, Нижневартовск/ХМАО, услуги и подтверждённый телефон |
| Responsive | 390 px и 1440 px без горизонтального скролла |
| Rollback | Старый лендинг можно вернуть без отката Studio и API |
| Release | Только после отдельного подтверждения владельца выполняются commit, PR и push |

## Рекомендуемый ближайший порядок действий

Сначала оставить альтернативный лендинг в ветке `ux-alternative-homepage` и добавить только Studio entry-context adapter. Затем выполнить существующий `check:pr`, расширить smoke-тесты для параметров `product` и `material`, проверить SEO artifact и открыть preview владельцу. После подтверждения визуального и функционального результата можно обсуждать замену production `/`.

Не рекомендуется сразу переписывать текущий `index.html`, менять canonical, подключать новые аналитические идентификаторы или перестраивать Studio. Основная ценность безопасной миграции — в том, что новый маркетинговый слой может развиваться отдельно от уже дорогой и проверенной производственной логики.
