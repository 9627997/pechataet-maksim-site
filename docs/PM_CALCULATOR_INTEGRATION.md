## 2. Контур расчёта

\`\`\`text
Браузер /calc/
    → GET /api/calc/ → доступные предварительные сочетания
    → выбор/изменение корзины
    → POST /api/calc/ → одна клиентская итоговая предварительная сумма
    → клиент вручную отправляет состав или открывает Studio
\`\`\`

- На входе автоматически собирается редактируемый пример: **25 м ленты + 250 стикеров**. Он не является обязательным составом.
- Лента: минимум **5 м**, шаг **5 м**; стикеры: минимум **50 шт.**, шаг **50 шт.**; максимум **3+3** самостоятельных позиций.
- Состав пересчитывается **целиком** на защищённом сервере, а не суммой отдельных публичных тарифов. Сервер сохраняет конфиденциальные параметры вне браузера.
- Существующий каталог предварительной оценки на 19.11.2026: **124** предложения — 92 сатиновые ленты и 32 стикера. Различные материалы не объединяются автоматически по цвету. Силиконовый материал — отдельное направление, пока не включённое в публичные варианты.
- Цена обозначается как **предварительная**; реальные остатки, техническую возможность печати, финальную сумму и срок подтверждает изготовитель.
- Результат котировки содержит \`canSubmitOrder:false\`: **сам калькулятор не принимает заказ**.
- При недоступности ценового API интерфейс показывает понятный fallback с телефоном и ссылкой на Studio, а не фиктивную цену.

Файлы: \`calc/index.html\`, \`calc/visual.css\`, \`calc/calc.js\`, \`api/calc/index.php\`, \`api/calc/.htaccess\`.

## 3. API и защита

\`GET /api/calc/\`: \`status: "catalog"\`, массив \`offers\` только из публичных полей \`type\`, \`geometry\`, \`base\`, \`print\`. Не добавлять сюда внутренние цены единицы, себестоимость, маржу, коэффициенты или складские данные.

\`POST /api/calc/\`: JSON с \`orderItems\`, каждым \`itemId\`, \`productType\`, \`quantity\`, \`configuration\`; ответ \`status: "estimate"\`, \`finalClientPrice\`, \`currency: "RUB"\`, \`canSubmitOrder: false\`. Публичный PHP проверяет структуру, допустимое количество, Origin, тип запроса и частоту обращений. Невалидный ввод отклоняется без расчёта «на глаз».

Расчётные функции, точность округления, каталог-источник, правила ценовых групп и проверка версий реализованы **в приватном серверном контуре**, не в этом репозитории. Изменение публичного интерфейса не должно обходить серверную проверку.

## 4. Граница Calc / Studio / заказы

На сегодняшний день это **два связанных навигацией, но не объединённых состоянием** пользовательских процесса:

1. **Calc:** предварительная сумма и состав, копирование текста, стандартный share в Telegram, открытие Studio с типом \`ribbon\`, \`sticker\` или \`bundle\`.
2. **Studio:** создание текста/логотипа, настройка ленты и стикеров, SVG/PNG/JPEG/первая страница PDF, маска/trace, preview и production SVG.
3. **Order receiver:** Studio передаёт структурированный заказ и файлы на \`POST /api/orders/\`, где заявка валидируется и сохраняется вне document-root. Повтор по одному \`requestId\` не создаёт дубль.
4. **Notifications:** Telegram, Google Drive/Apps Script и MAX обслуживаются серверной очередью и worker. **Приватное сохранение и серверный номер заявки**, а не сообщение в мессенджере, означают успешный приём.

**Отсутствует в текущем Calc:** серверный \`quoteId\`, самостоятельная форма обращения, гарантированная доставка расчёта изготовителю, перенос всей спецификации в Studio, автоматическое принятие или резервирование заказа. Делать вид, будто универсальный Telegram share доставил заявку в компанию, нельзя.

При будущей интеграции физические размеры и product IDs необходимо нормализовать: отдельные варианты в Studio исторически обозначались иначе, чем в Calc. Точное соответствие нельзя выводить только из заголовка товара.

## 5. Безопасная публикация

- \`main\` защищена обязательным Pull Request и проверками.
- \`.github/workflows/studio-tests.yml\` выполняет lint, style, build и Playwright smoke; полный регресс выполняется отдельно.
- \`scripts/build-deploy.mjs\` формирует **публичный allowlist** \`_site\`, исключая закрытые источники, документацию и тестовые данные.
- \`.github/workflows/deploy-reg-ru.yml\` сначала проверяет и безопасно устанавливает закрытый pricing package за пределами web-root, затем обновляет публичные файлы и выполняет production smoke. В pipeline есть проверки приватных путей, работоспособности калькулятора и сохранности Studio/API заявок.
- Нельзя копировать приватный модуль в \`calc/\`, \`api/calc/\`, \`_site/\` или любую раздаваемую папку.
- Любое изменение режима расчёта требует отдельной проверки реального POST и подтверждения, что \`canSubmitOrder\` не стал \`true\` без согласованного процесса заказа.
- Для отказа сервера используется понятная ошибка/fallback, а не число, вычисленное в браузере.

Историческая трассировка релизов: PR #193 → #194 → #195 → #196, деплой #209 (финальный smoke не прошёл) → #210 → #211 → **#212 SUCCESS**.

## 7. Предлагаемое развитие — до отдельного согласования

**P0. Превратить расчёт в доставленное обращение.** Добавить с главной видимый переход в Calc; после суммы — «Обсудить заказ», короткий серверный \`quoteId\`, контакт/согласие, подтверждённый номер обращения и уведомление продавца. Не путать лид с production-order.

**P1. Связать Calc → Studio.** Полная спецификация по короткому токену, стабилизированные variant IDs и проверяемое соответствие физическим форматам. Никаких персональных/больших JSON в URL.

**P1. Надёжное обновление цен.** Контролируемый экспорт из закрытого Numbers, тестовая копия, сопоставление вариантов, независимая сверка, версионирование снимка, smoke и rollback. Не превращать публичный GitHub в источник себестоимости.

**P1. Измерение экономики.** Реальные затраты труда, переналадки, брака и упаковки; сравнение нынешней цены и возможного улучшения **в теневом режиме**. Не менять цену автоматически без утверждения.

**P2. Расширение ассортимента.** Отдельные силиконовые ленты после проверки материалов/идентификаторов, B2B-пакеты, повторы заказа и кейсы с реальными фотографиями.

**Метрики:** доля успешных расчётов; quote→доставленное обращение; обращение→подтверждённый заказ; отклонение предварительной/итоговой цены; вклад после переменных затрат; доля 5xx и P95 latency.

> **На согласование:** начать с P0 — отдельный запрос на обсуждение после расчёта, **без изменения** работающего алгоритма Pricing 2.0 или receiver Studio. Финальная схема \`quoteId\`, срок его жизни и каналы уведомлений требуют отдельного решения владельца.
